## 主要发现

### 1. P1：旧分析结果可写回新会话，忙碌期间的新请求可能丢失

- 证据：`capture/ChatCaptureService.kt:243–282`，`runAnalysis()` 在 `analyzing` 时直接返回；两路回调直接更新同一个 overlay，没有请求代次或会话身份校验。完成后只将 `analyzing` 清零，不消费较新的 `pendingSnapshot`。
- 触发：A 会话分析未结束时切到 B，或 A 收到新消息。B 的防抖任务在忙碌时返回，A 的结果随后仍能显示在 B；新内容的签名已经记录，后续同内容事件又被去重。
- 影响：展示错误上下文的判断和候选回复，最新请求停留未执行。`fillInput()`（第 475 行起）重新查找当前窗口的可编辑节点，没有绑定生成回复时的会话，旧候选可能填入新窗口；代码未自动发送。
- 最小修法：为会话与分析请求建立身份/代次，过期回调不更新 UI；请求完成后处理最新待分析快照；填入前重新校验目标，目标变化则取消填入。
- 回归：A→B 切换、同会话连续来消息、判断失败而回复仍在运行、点击填入后立即切窗。

### 2. P1：相同正文的不同会话被当成同一快照

- 证据：`core/ChatModels.kt:35–37` 的 `signature()` 只拼最后六条消息；`capture/ChatCaptureService.kt:193–206` 仅在包名变化时重置签名，并在重置旧 UI 之前按签名返回。
- 触发：同一应用的 A、B 两个聊天最后几条内容相同，例如都只有“好的”。
- 影响：`currentSnapshot` 已指向 B，但悬浮窗仍可保留 A 的分析与填入回调。
- 最小修法：将会话身份与内容签名分离，先处理会话变化，再对同一会话的内容去重；标题不可靠时不要据此认定身份相同。

### 3. P1：缺失标题会沿用上一联系人的身份

- 证据：`capture/ChatCaptureService.kt:234–239` 的 `lastGoodTitle` 按包名缓存；新页标题为空或处于“连接中”时，无条件复制上一个有效标题。之后 `prefs.isAllowed()` 用这个标题判断白名单，`ContextBuilder.build()` 用它匹配联系人并记录历史。
- 触发：从联系人 A 切到 B，B 的正文已可读但标题尚未加载或未识别。
- 影响：B 的消息可能匹配 A 的白名单、联系人背景与历史；开启历史后可能归档到错误联系人。
- 最小修法：仅在已确认同一会话内允许临时标题复用。身份未知时暂停联系人匹配、历史写入和依赖身份的自动分析，不能跨页面沿用。

### 4. P2：回复先于判断完成时被丢弃

- 证据：`overlay/OverlayController.kt:362–373`，`showReplies()` 在 `lastJudgment == null` 时直接返回，没有缓存回复；后到的 `showJudgment()` 又以 `generating = true` 渲染。
- 触发：生成及排序请求比独立判断请求更快结束。
- 影响：本轮回复已返回，但界面仍显示生成状态，没有候选可用。两个并行请求不存在固定完成顺序。
- 最小修法：按同一请求 ID 分别保存两路结果和完成状态，任意回调到达均从完整状态重新渲染。

### 5. P2：离开聊天或关闭助手没有使待处理工作失效

- 证据：`capture/ChatCaptureService.kt:124–170`，关闭助手只隐藏窗口，非适配应用只隐藏/显示 idle，适配器返回 `null` 时直接返回；都不清理待分析快照和防抖任务。`runAnalysis()` 不复查 `prefs.enabled`。`onDestroy()` 也没有清除主线程延迟任务。
- 触发：在 800ms 防抖期间离开聊天、关闭助手，或在网络/OCR 请求期间进行这些操作。
- 影响：旧请求仍可能启动/完成，回调可能重新显示悬浮窗；非聊天页仍保留旧快照供手动分析或存联系人使用。
- 最小修法：在退出聊天、关闭、销毁时失效会话代次并清理待处理状态；启动和回调处复查生命周期及启用状态。与问题 1 共用状态管理，避免重复兜底。

### 6. P2：无气泡矩形的自动 OCR 会漏掉后续内容变化

- 证据：`capture/ChatCaptureService.kt:183–186、313–318`，无矩形时 OCR 签名只有包名与标题；相同签名且悬浮窗存在即跳过截图。
- 触发：微信等适配器返回“聊天页、空消息、无矩形”，第一次 OCR 完成后同一标题收到新消息或滚动。
- 影响：正文已经变化但自动 OCR 不再刷新，需手动截图或其他状态变化才能恢复。
- 最小修法：将限频与内容有效期分开，使用有上限的刷新间隔或可靠内容变更信号，既允许新内容采集，也避免每个光标事件都截图。

### 7. P2：日志中仍有可识别的聊天信息与未脱敏错误响应

- 证据：`capture/ChatCaptureService.kt:208` 直接输出 `snapshot.title`；`jev/HttpJson.kt` 将错误响应正文放进 `ApiException`，`jev/JudgeClient.kt:45` 又把 `e.message` 写入 logcat。
- 影响：联系人/群名称确定会进入日志；若模型服务在错误正文回显聊天或凭据，相关内容也可能进入日志。未观察到真实密钥泄露，后者属于条件性风险。
- 最小修法：日志只保留请求代次、路由、状态码和数量；日志与 UI 错误输出统一脱敏，不能信任服务端错误正文不含敏感信息。

### 8. P2：文档中的直接 Wrapper 命令在当前 Unix 检出中无法执行

- 证据：`git ls-files -s gradlew` 为 `100644`，文件权限为 `-rw-r--r--`；README 和开发指南使用 `./gradlew`。
- 影响：macOS/Linux 按文档直接执行会因缺少执行位失败，尚未进入 Gradle。
- 最小修法：后续将 Wrapper 执行位纳入 Git，或统一说明使用 `sh gradlew`。本轮 AGENTS 已使用后者，但没有改动 Wrapper 或重写既有构建说明。

### 9. P2：联系人写入失败仍提示保存成功

- 证据：`core/kb/KbStore.kt:122–144`，`saveOrMergeContact()` 忽略 `saveContact()` 返回的 Boolean，仍返回“已存为联系人”或“已并入联系人”。底层 `writeAtomic()` 捕获写入失败并返回 false，调用者不会收到异常。
- 触发：存储空间不足、写入失败或损坏文件无法备份时点击存联系人。
- 影响：用户看到成功提示，但数据未持久化；服务层的异常捕获无法纠正这个提示。
- 最小修法：逐层传递保存结果并据此显示成功/失败，核对知识库编辑页对其他 Boolean 写入结果的处理。
